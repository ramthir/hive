# Hive

File-backed notes app: markdown files in `NOTES_DIR` (default `~/Workspace/notes`), versioned with git (one commit per save/rename/delete). Based on ~/Workspace/pandora's notes feature, without the database.

- Tests: `uv run pytest` (single file: `uv run pytest tests/<path>`). It also runs the Node unit tests in `tests/js/` (`tests/test_js_units.py`; skipped without `node`). Browser tests in `tests/browser/` need `uv run playwright install chromium` and are skipped when Chromium cannot launch, so a green run may not have exercised the UI.
- Every new feature needs automated tests next to the existing ones in `tests/`.
- Layers: `src/domain` (entities, ports) -> `src/application` -> `src/infrastructure` (git, fs_notes) -> `src/api`.
- A note's title is its first `# heading`; its file name is the kebab-case of that title (never set by hand). Changing the heading renames the file (service rewrites `[[slug]]`/`[[Title]]` links). Notes whose file has no heading show the frontmatter title as one until saved. `/` and `/notes` open the most recently edited note: there is no list page.
- Note identity is the filename slug. Frontmatter (`title`, `tags`, `created`, `updated`) is round-tripped with ruamel so diffs stay minimal.
- Never run tests against the real notes dir; use temp git repos.

## API
Under `/api`: `GET/POST /notes`, `GET/PUT/DELETE /notes/{slug}`, `/notes/{slug}/backlinks`, `GET /notes/{slug}/properties`, `/notes/{slug}/versions[/{sha}[/diff]]`, `POST /notes/{slug}/versions/{sha}/restore`, `GET /latest`, `GET /resolve` (wiki links), `GET /tasks`, `GET /tasks/current-week`, `GET /time-entries`, `GET /time-notes`, `PUT/DELETE /notes/{slug}/time/{day}`, `POST /notes/{slug}/time`, `GET /tags`, `GET /types`, `POST /reindex`, `POST /diagram/render`, `POST /diagram/render/png`, `GET /diagram/status`, `GET /metrics`, `GET /system/stats`, `GET /system/processes`, `GET /agents/usage`, `GET /agents/usage/sessions`, `GET /agents/quota`, `GET /colab/usage|sessions|stream|health`, `POST /chat` (SSE; optional `note`, `selection`), `DELETE /chat/session[?note=]`, `GET /chat/status`, `GET /events` (SSE), `GET /iptv/status|channels|groups`, `POST /iptv/sync`, `GET /iptv/series/{id}`, `GET /iptv/stream-url`, `GET /health`. Pages: `/library` (`/iptv` redirects there), `/`, `/notes[/...]`, `/tables/{slug}`, `/tasks`, `/time-entries`, `/dashboard[/agents|/colab]`, `/chat`. `/tags` and `/types` feed the note page's tag and type comboboxes.
**Deleting a linked note is refused:** `DELETE /api/notes/{slug}` answers 409 (`NoteLinked`, checked in `NoteService.delete`) naming the notes that still link to it (a self-link does not count). The note page's delete button asks `/backlinks` first and, if there are any, shows a "Cannot Delete Note" dialog listing them as links (clicking one closes the dialog and opens that note) instead of the confirmation.
`GET /api/notes/{slug}` returns a `revision` (hash of the file's text). `PUT /api/notes/{slug}` accepts it back: if the file changed since (another tab, an editor, `git pull`), nothing is written and the answer is 412; the note page then asks before overwriting. Requests without `revision` (task board, drawers) are never refused.

## Live changes (SSE)
`GET /api/events?note=<slug>&type=<type>` streams `change` events when notes change, whether Hive saved them or something else did (editor, `git pull`, another tab): `NoteService.invalidate` is the one place both pass through (the watcher and every service write call it), so it publishes to `ChangeFeed` (`src/application/notes/feed.py`). `note=` sends only that note (the note page), `type=task` only notes that have or just lost that type (the task board), neither sends all. An event is `{slug, title, revision, deleted, types}`; `{reset: true}` means anything may have changed (`POST /api/reindex`, the end of a chat run, more than `PATCH_LIMIT` notes, a viewer that fell behind, or a reconnect on the client): look again. Nothing is read while nobody listens, and an event that repeats the last revision announced for a note (a save, then the watcher seeing the same file) is dropped. With `HIVE_WATCH=0` outside edits give no events.
- **Note page** (`watchNote` in `static/notes/notes-page.js`; DOM-free parts in `static/events.js`, tests `tests/js/events.test.mjs`): listens for the open note only. An event (debounced 400 ms, and put off while a save is in flight) fetches the note and compares its `revision` with the one the page holds, so the page's own saves are recognised: same revision does nothing, a clean note is redrawn in place (scroll and edit mode kept), a note with unsaved edits gets a banner (Reload / Keep editing) and nothing is thrown away, a deleted or renamed note goes back to `/notes` (or, with unsaved text, a banner). Saving over an outside change still gets the 412 prompt.
- **Task board:** listens for `type=task` and asks `/api/tasks` again (not while a card is mid-move).

## Performance monitoring
- Live: `GET /api/metrics` -> counters (`watcher_batches`, `watcher_events`, `index_invalidations`), timings (`index_rebuild`, `git_commit`: count/avg/max ms) and process stats (`cpu_s`, `rss_kb`, `threads`). Poll `cpu_s` twice to get CPU use over an interval.
- Benchmark: `uv run python scripts/bench.py <COPY of notes> [--with-hook] [--no-watch]` (edits files and commits: use a copy).
- Design: the watcher (watchfiles/inotify, `step=250ms`, `debounce=400ms`) only invalidates the index; it is rebuilt lazily on the next request, so bursts coalesce into one rebuild and an idle app does nothing. The rebuild is incremental twice over: `FileNoteRepository.list()` re-parses only files whose (mtime, size) changed, and the watcher and service writes name the slugs they touched, so `NoteIndex.updated` patches just those notes (`index_patch` timing; copy-on-write, so readers never see a half-updated index). More than `PATCH_LIMIT` (50) changed notes, `POST /api/reindex` or a file the repository cannot load by name fall back to a full rebuild.
- `commit --only` runs hooks on a temp index, so `GitClient.commit_paths` re-syncs the real index afterwards; do not remove that or formatter hooks leave phantom staged changes.

## Layout
Hive is a desktop app: there is no mobile or narrow-screen layout (no `@media` width queries, no sidebar menu button). Pages are laid out for a wide window and the sidebar is always a left column that can be collapsed (Ctrl/⌘+\\ or B). Do not add breakpoints.

## Running
`NOTES_DIR=~/Workspace/notes uv run python main.py` serves on port 80 (needs `net.ipv4.ip_unprivileged_port_start` <= 80 or root). Binds 0.0.0.0 by default (a container's published port arrives from the Docker gateway, not loopback) and there is no auth, so `LocalhostOnly` (`src/api/localhost.py`, tests `tests/api/test_localhost_only.py`) answers 403 unless the `Host` (and `Origin`, when sent) is `localhost`, `127.0.0.1` or `::1` (`HIVE_ALLOWED_HOSTS` adds names). Publish the port on the host's loopback (`-p 127.0.0.1:80:80`) so nothing else connects at all; `HOST=127.0.0.1` closes the socket too. `PORT` overrides the port. `HIVE_WATCH=0` turns the file watcher off (edits made outside Hive are then only seen after `POST /api/reindex`). `GRAPHVIZ_DOT` points at Graphviz `dot` when it is not on PATH. Every save is a real git commit in `NOTES_DIR`.

`scripts/service.sh start|stop|restart|status|ensure` runs it in the background without systemd (pid and log in `~/.local/state/hive/`; it also finds a `main.py` started by hand from this directory). It does not survive a reboot or a container restart: start it again.

## PlantUML previews
Fenced ```plantuml / ```puml blocks render as images in the preview. `DiagramService` (`src/application/diagrams`) runs `java -jar plantuml.jar -pipe -tsvg` per diagram (~200 ms) under `PLANTUML_SECURITY_PROFILE=SANDBOX`, so the renderer itself reads no files and opens no URLs; `!include <file>.puml` is inlined by us, only from `NOTES_DIR` and never outside it, and `!include monokai-theme.puml` / `!theme monokai-pro` always use the bundled theme (as in Pandora). Results are cached by source hash. The SVG is shown through an `<img>` data URL, never inline, so a diagram cannot run script.
**PNG download:** hovering a rendered diagram shows Dark / Light buttons; `POST /api/diagram/render/png` (`{source, theme}`) renders `-tpng` with no frame (`DiagramBorderColor transparent`), `light` adds `!define THEME_LIGHT` before the monokai theme, and the dpi is raised to 300 when the image still fits under ~4000 px a side (else the largest dpi that does; an author's own `skinparam dpi`/`scale` is kept). Not cached. The file is `<note title>-<theme>.png`.
Setup (no root needed): a JRE (`mise install java@temurin-21`) and `plantuml.jar` in `~/.local/share/hive/plantuml/` (verify the SHA-256 GitHub publishes for the release), then `PLANTUML_JAVA` / `PLANTUML_JAR` in `.env`. Without them the code block stays and a message says why.
Fonts (`apt-get install fontconfig fonts-dejavu-core`, needs root) are required too: on a machine without fontconfig Java dies with `Fontconfig head is null` and every diagram fails with "PlantUML produced no image". Graphviz (`apt-get install graphviz`, needs root) is needed for the theme's boxed connectors: PlantUML still draws class/component diagrams without it, but with a layout that ignores `LineType ortho`, so lines come out diagonal. `/api/diagram/status` reports `graphviz`, and a real-Java test fails if it is missing. Mindmaps do not use Graphviz; their connectors are always curved.

## Frontmatter conventions (match the vault)
`tags` is an inline list (`tags: [a, b]`); `type` is a single value (`type: task`), or an inline list when a note has several. Hive reads block lists, inline lists and scalars, and only rewrites `tags`/`type` when they actually change; a changed value is written in the convention above. Types map to icons and icon colours (`TYPE_COLORS`, palette tokens; shown in the note search) in `static/type-icons.js` (add a vault type there; `tests/js/type-icons.test.mjs` fails if a name is not in the vendored Font Awesome).

## Task board
`/tasks` (`static/tasks.html`, its own document, so sidebar links to Notes are full navigations) shows every note of `type: task` as a card on a To Do / In Progress / Done board (`GET /api/tasks`; board component from Pandora). Dragging a card sends `PUT /api/notes/{slug}` with `status`: one normal git commit.
- **Status:** frontmatter key `status` (`TODO`, `IN_PROGRESS`, `DONE`), written after `type` and only when it changes. Notes without one (older vault notes) get a derived status: `done` in `tags` means Done, else To Do. A stored status wins over the tag.
- **Week:** `week: 2026-W47` (ISO week a task was finished), written after `status`. Set when a task moves to Done (the service's clock), cleared when it leaves Done, or set by hand through the API. The server does all the week maths: each task carries `week_key` (its `week`, else the week of `updated`) and `week_stored` (which of the two); `GET /api/tasks/current-week` gives the Done pill's default. The page never computes weeks and reloads `/api/tasks` after a save.
- **Done pill:** Pandora's week dropdown in the Done header (weeks with finished tasks, newest first with counts, this week always listed, then All weeks). Starts on this week; the choice lives in the address (`/tasks?done=2026-W47` or `?done=all`). Open tasks are never filtered.
- **Priority:** frontmatter key `priority` (`must`, `important` or `nice-to-have`), written after `status` and only when it changes. Older vault notes mark it with a tag of the same name (leading `#` ignored; the most urgent wins); a stored `priority` wins over the tag, and `/api/tasks` leaves priority tags out of `tags`. `PUT /api/notes/{slug}` takes `priority` (`""` removes it): it sets the key and drops any priority tag from the given (or current) `tags`, so a note migrates the first time its priority is saved (`src/domain/notes/tasks.py`). Cards show a ranked chip; each column sorts Must, Important, Nice to have, none (stable) in the page, not on the server.
- **Card and drawer:** Cards show priority, project, ticket, week, and remaining tags in that order when present. Card logic in `static/tasks/card.js` (tests: `tests/js/task-card.test.mjs`). Clicking a card opens the note properties drawer (`openProperties`, the same code as the note page); it sends only the changed keys in one `PUT` (one commit, plus the rename commit when the title changes). The card's arrow goes to the note. Week is editable there too.

## Read pages (table and timeline notes)
Note types read on their own page share their code: `READ_PAGES` in `static/notes/read-pages.js` lists each type (`type`, `path`, `matches`) and `readPagePath(note)` gives the address the note page redirects to in read mode (tests: `tests/js/timelines.test.mjs`). `defineReadPage({tag, type, View, viewOptions, onSaved})` in `static/notes/read-page.js` is the page itself: load, redirect when the note is not of the type or is missing, copy, delete, properties, history and the pencil (`/notes/{slug}?mode=edit`); a view's own callbacks go in `viewOptions(app)`. To add a type: an entry in `READ_PAGES`, a page script calling `defineReadPage`, an html file, and its `(prefix, html)` in the route loop in `src/api/main.py` (kept in step by hand).

## Timeline notes
A note whose `type` includes `timeline` is read on its own page, `/timelines/{slug}` (`static/timelines.html`, its own document like `/tables/{slug}`; code in `static/timelines/`), and `/notes/{slug}` redirects there in read mode; the pencil goes to `/notes/{slug}?mode=edit`. A note that is not a timeline is sent back to `/notes/{slug}`. `timeline-note.js` (DOM-free; tests: `tests/js/timelines.test.mjs`) reads each `## Label — Title` heading with the paragraph and bullet list under it as a phase; the view draws phase cards on a rail. It is read-only: the markdown is the only source, edited through the note page.

## Time entries
Time is logged on notes of `type: task` or `meeting` (a note that is both counts as a task) in the `time` frontmatter key: a map of ISO day to minutes, one total per day, written inline after `week` (`time: {2026-11-20: 90, 2026-11-21: 45}`). Days are 1-1440 minutes. Domain in `src/domain/notes/time.py`; the repository only rewrites the key when the usable days change and keeps entries that are not a valid day and minutes (a hand-typed `soon: 30` survives). Logging time is a normal save, so it is one git commit and bumps `updated` like any save.
- **Write:** `NoteService.log_time(slug, day, minutes, add=False)` / `remove_time`. `PUT /api/notes/{slug}/time/{day}` sets the minutes (1-1440), `POST /api/notes/{slug}/time` (`{day, minutes}`) adds to the day, `DELETE .../time/{day}` removes it (404 if the day is absent). `POST .../time/{day}/move` (`{slug, day, minutes}`) moves a day to another note and/or day, adding to what is there, in one commit (`NoteService.move_time`, `FileNoteRepository.update_many`). Time left on a note that is no longer a task or meeting still shows as a row of type `other` (warning icon) so it can be deleted; it is not offered in the picker. A note that is not a task or meeting, a bad day or a day over 1440 minutes is a 422. `GET /api/notes/{slug}` returns the map as `time`.
- **Read:** `GET /api/time-entries?q&start&end&note&page&page_size` returns one row per note and day (`id` is `slug:day`; newest day first, then title) plus the current month (the server's clock: `month`, `today`) over every match: `total_entries`, `total_minutes`, `task_minutes`, `meeting_minutes`, `today_minutes` and `days` (each day with time: its minutes and the `{title, project, minutes}` it was spent on). `q` is free text on the title plus Pandora's `project:`, `task:`, `date:today|yesterday|YYYY-MM-DD`, `duration:>30m` (`<`, `>=`, `<=`, `45`, `30m-2h`) filters; an unreadable `date:` or `duration:` matches nothing; a filter swallows the text after it, so put free text first (quote a multi-word value: `project:"Big Co"`). `project` is an optional `project:` frontmatter key. The search and summary live in `src/application/notes/time_entries.py`.
- **Page:** `/time-entries` (`static/time-entries.html`, `static/time-entries/`): Pandora's three stat cards (`static/components/stat-card.js`, `activity-sparkline.js`: Total Logged with the month's sparkline and the 160h month / 8h day progress, Task Work, Meetings; built by `summaryTiles` (`summary.js`) from the server's month, so the page does no date maths), the table, paging and an add/edit drawer, using Pandora's table, pagination, date/duration pickers and CRUD drawer (copied into `static/components/`). The search and page are kept in the address (`?q=&page=`). The drawer's note picker comes from `GET /api/time-notes`: tasks and meetings only, this week's first (edited this week or with time logged this week, by the service's clock; newest first), then the rest by title, with "This week" / "Earlier" headings (a `group` on a combobox option draws a heading where it changes). Logic without DOM is in `static/time-entries/` (`format.js` durations and days, `summary.js` the stat cards, `logged.js` the note page's helpers, `entries.js` table, address and `savePlan`; tests: `tests/js/time-entries.test.mjs`); `savePlan` turns the drawer into API calls (adding adds to the day; moving a row to another note or day adds there and removes the old row). On the note page a task or meeting note has a clock button ("Log time", `static/notes/log-time.js`: date and duration, adds to the day) and a "3h 30m logged" chip in the footer; logging commits only the `time` key and leaves unsaved editor text alone.

## Note properties drawer
The sliders button in a note's footer (Ctrl/⌘+Shift+P) opens Pandora's properties drawer, titled for the type ("Task Properties", "Contact Properties"...; `title` of `GET /notes/{slug}/properties`), with fields that depend on the note's `type`. Pandora keeps these as links between notes; here each field is a frontmatter key (`project: Acme`), so there is no database and a note that links by title does not follow a rename.
- **Forms:** `src/domain/notes/properties.py` (`FORMS`, keyed by lower-case type; the first of a note's types with a form wins, so task beats meeting). Task: project, specification, ticket (Ticket ID, free text), status, priority, assignee, week, tags. Meeting: week, project. Project and Company: billing (Billable / Non Billable / Prospecting). Every "Project" picker (task, meeting, contact, spec, prompt) lists notes of type `project` or `company`, since work is booked against a client company too. Contact: role (a `values` field: the roles other notes already have, or a new one; likewise team), project (several allowed: a `multiple` note field, stored as `project: [A, B]`, one title stays a plain value), billing (adds Shadowed), acting_for (shown and required only while billing is Shadowed). Spec: project, application. Prompt: project. A type with no form has no button (`has_properties` on `GET /api/notes/{slug}`). Add a type there and the drawer follows; the page has no per-type code.
- **Field targets:** `tags`, `status`, `priority` and `week` are the keys the task board already manages (changed tags are sent with the priority, since the server drops a priority tag from the tags it is given), so the drawer and the board agree; every other field is its own key and lands in `extra`. A `note` field is the title of a note of the given types (the choices come from the index; a hand-typed value stays selectable); a `select` field is a fixed list.
- **API:** `GET /api/notes/{slug}/properties` returns the groups and fields with `value` and `choices` (404 if the type has no form). `PUT /api/notes/{slug}` takes `properties` (`{"project": "Acme"}`, `""` removes a key; unknown keys, bad select values and a missing required field are 422) next to `status`/`priority`/`week` (`week: ""` clears it). `src/application/notes/properties.py` builds the form view.
- **UI:** `static/notes/properties.js` (drawer) and `property-fields.js` (DOM-free: visibility, `propertyChanges`, field markup; tests: `tests/js/property-fields.test.mjs`). Saving sends only the changed fields in one PUT, so it is one commit. Unsaved editor text is saved first.

## Agents
The Agents tab of the dashboard (`/dashboard/agents`, `<agents-tab>` in `static/agents/`) shows this month's token usage of the coding agents Claude, Codex and Antigravity: a card per provider (Totals, Input, Cached, Output, sessions, models), a stacked daily chart for the month and a server-sorted, paged sessions table whose session cell copies the resume command (`claude --resume <id>`, `codex resume <id>`). Ported from Pandora's Na'vi tab without its task links. Each card has Pandora's quota rings beside Totals (below). `GET /api/agents/usage` is the view, `GET /api/agents/usage/sessions?sort&dir&page&page_size` one page of sessions (`sort`: last_activity, provider, input, cached, output, total).
- **Source:** `ccusage` (npm `ccusage`, found on PATH, then in an nvm or mise node; `HIVE_CCUSAGE` sets it) run as `ccusage --sections daily,session --by-agent --json --no-cost --offline --since <1st of month> -z <host timezone>` (`CcusageCollector`, `src/infrastructure/agents/usage_files.py`). It reads the agents' own session logs, so nothing is configured. Without it the page says so.
- **Cache and refresh (quarter hour):** the report is `~/.local/state/hive/agents/usage.json` (`HIVE_STATE_DIR`, the folder `service.sh` uses), replaced atomically and parsed again only when its size or mtime changes (`ReportStore`). `AgentUsage` (`src/application/agents/usage.py`) serves it. `RefreshSchedule` (`src/application/agents/refresh.py`, started by the app lifespan, only with the real collectors) wakes at :00, :15, :30 and :45 (and once at start) and makes a new report in a background thread; between boundaries a request only reads the cache. A report made before the current slot is "due", so a request that finds one (the app was off or asleep at the boundary) starts the catch-up itself. A request never waits for ccusage: only a missing report or a new month waits (requests then share one run). A failed run keeps the old report, shows its reason once the report is over 45 minutes old, and is not retried for a minute. The timer runs ccusage every 15 minutes even with no tab open; the page polls once a minute while its tab is visible. `/api/metrics` counts `agents_refreshes` and `agents_refresh_errors` and times `agents_collect`.
- **Quota rings:** `GET /api/agents/quota` gives each agent's 5-hour and weekly window (`state` ok / stale / expired / unavailable, `used_pct`, `resets_at`); the card draws what is left as concentric rings (Antigravity has a third, Argon's weekly) with a tooltip per ring, a placeholder while the first run is collecting, and a quiet info icon with the failure reason tooltip when a provider is unavailable. Our own collector replaces Pandora's `ops quota collect` and reads only the agents' CLIs, never a login token or an API itself (`QuotaCollector`, `src/infrastructure/agents/quota_sources.py`): Claude `claude -p /usage --no-session-persistence` (0 tokens, saves no session, so it never shows on the Sessions table), Codex `codex app-server` JSON-RPC `account/rateLimits/read` (else the newest `rate_limits` event in `~/.codex/sessions`), Antigravity `agy -p /usage` (Gemini's 5h and weekly plus Argon's weekly; the Claude and GPT pool is not shown). `CLAUDE_BIN`, `AGY_BIN`, `CODEX_BIN` and `CODEX_SESSIONS` override where they are. The three run at the same time; one that fails is `unavailable` with its reason and never hides the others, a window whose reset has passed is `expired` with no value, and a reading is never carried forward. Same cache and refresh as the usage report (`RefreshingReport`, `src/application/agents/refresh.py`; `~/.local/state/hive/agents/quota.json`), except the first request does not wait: reading the CLIs takes seconds (Antigravity up to a minute), so it starts the run, answers "The quota is being collected." and the tab asks again after 8 s. The quota is its own request, so a slow CLI never holds the usage back. A snapshot over 45 minutes old shows no values. `/api/metrics` counts `agents_quota_refreshes` and `agents_quota_refresh_errors` and times `agents_quota_collect`.
- **On the page:** the month panel says how old the report is (`Updated 7m ago`, kept current by the minute poll alongside stale-banner ages and quota reset countdowns, full time on hover) and highlights today's tick (`data-today`); tooltips on Totals, Models, daily bars and quota indicators are keyboard-focusable; a quota ring turns orange under a quarter left and red under a tenth (`quotaLevel`); the sessions table stays mounted across overview/quota updates (reconciling open tooltips); a refresh that fails keeps the last report and quota rings on screen and says so in the dashboard header; the quota is asked for again every 8 s only while the server says the first run is under way, 8 times at most; the sessions table is redrawn each minute so its relative times move.
- **Manual run:** `uv run python scripts/agents_collect.py [usage|quota|all] [--output FILE] [--ccusage PATH]` makes the report(s) now and prints what it found (default `all`; `--output` is a folder for `all`; exit 1 with the reason if one fails, the other still runs).
- **Domain:** `src/domain/agents/usage.py` (`parse_envelope`, `build_view`, `session_page`). ccusage's `input` excludes cache; the view's `input` includes cache reads and writes, and `total` is input plus output. A report whose month is not the current one is never shown as this month's. `session_page` extracts sessions without re-aggregating daily usage and sorts `last_activity` chronologically in UTC with missing timestamps last.
- **Tests:** `tests/domain/test_agent_usage.py`, `tests/infrastructure/test_agent_usage_files.py`, `tests/application/test_agent_usage.py`, `tests/domain/test_agent_quota.py`, `tests/infrastructure/test_agent_quota_sources.py`, `tests/application/test_agent_quota.py`, `tests/api/test_agents_api.py`, `tests/test_agents_collect_script.py`, `tests/js/agents.test.mjs`, browser tests in `tests/browser/test_ui.py` (they inject a fake collector; no test runs the real ccusage or reads `~/.local/state`).

## Colab
The Colab tab of the dashboard (`/dashboard/colab`, `<colab-tab>` in `static/colab/`) is Pandora's Colab dashboard: compute units (`colab usage`: balance, usage rate, active assignments), a picker for the active runtimes (`colab sessions`) and, for the picked runtime, live CPU / memory / storage / load (a GPU card replaces load when there is a GPU) and a process table. Needs the `colab` CLI, found at `COLAB_CLI_BIN`, on PATH or in `~/.local/bin`, and logged in: without a login the CLI asks for a Google authorization code on stdin, which Hive never answers (stdin is closed, 15 s timeout), so the cards read "Unable to read" and the header shows why.
- **Live numbers:** `GET /api/colab/stream?session=` (SSE, event `status`) makes the app's `ColabCollector` (`src/application/colab/collector.py`, `app.state.colab`) probe that runtime every 30 s while someone watches; viewers share one collector per runtime, it stops 10 s after the last viewer leaves (evicting `inactive` feeds so dead runtimes do not accumulate) and at app shutdown, and a new viewer gets the cached snapshot at once (re-subscribing to a previously `inactive` runtime resets it to `loading`). Last-good values are never replaced by a failed or malformed result. The stream is the only way to start a probe, and it answers 409 for a session that is not active, so Hive never starts a new VM.
- **Probe:** one fixed read-only shell snapshot (`nproc`, `uptime`, `top`, `free`, `df /content`, `nvidia-smi`, `ps`) sent on stdin through `colab exec` to a disposable namespace, framed by `===HIVE_PROBE_START/END===`; output that is not complete is an error. Before any probe the collector asks the runtime's kernel for its state and only an `idle` kernel is probed; a busy or unknown one pauses monitoring. That check (`get_colab_kernel_state`, `src/infrastructure/colab/cli.py`) reads the runtime's URL and token from `~/.config/colab-cli/sessions.json`, sends the token only to an `https://*.colab.dev` host that contains the runtime id (no redirects, 8 s timeout), lists kernels read-only and, only if there are none, starts one Python kernel once per runtime per app run; several kernels, or any doubt, pause monitoring. `colab exec` gets an owner-only temporary session file that pins the kernel just checked, so it cannot overwrite the user's own registry. A race with another client can still leave one probe queued. Hive has no login: anyone who can reach its port can open the tab and so start these probes (fixed commands only; there is no way to run anything else).
- **On the page:** the header line combines the stream's notice or error with what the polled usage and sessions reads say (and clears stale stream status when switching runtimes); when the CLI is unreachable, Active Assignments keeps "Unable to read" and the empty panel explains the session read failure instead of showing "No active session"; a runtime with no data yet (busy kernel, failed probe) shows the reason in the table instead of loading for ever; a stream that could not open or closed shows a Reconnect row (a closed `EventSource` never reconnects by itself, so `streamIsLive` treats it as down and the 30 s poll also reopens it); the GPU card covers every GPU (average load, `2× Tesla T4`, VRAM added up, coloured for either compute or VRAM pressure); the runtime process table has a client-side filter box with match counts.
- **CLI load:** `colab usage` and `colab sessions` are `SharedCall`s (`src/infrastructure/colab/cli.py`): callers that arrive together share one subprocess and a good answer is kept 10 s, so many tabs, the collector and every stream connect cost one run per 10 s; a failure is shared by those waiting and never kept.
- **Layers:** parsers and errors in `src/domain/colab/` (`parsing.py`, `errors.py`), the CLI runner, probe and kernel check in `src/infrastructure/colab/cli.py` (`httpx` is a runtime dependency for the kernel check), routes in `src/api/routes/colab.py`. The page (`static/colab/format.js` DOM-free, `colab-tab.js`, `colab.css`) filters, sorts and pages the at most 100 streamed processes itself and shows notices and errors in the dashboard header's status line (a `tab-status` event).
- **Tests:** `tests/domain/test_colab_parsing.py`, `tests/infrastructure/test_colab_cli.py`, `test_colab_kernel_state.py`, `tests/application/test_colab_collector.py`, `tests/api/test_colab_api.py`, `tests/js/colab.test.mjs` and browser tests in `tests/browser/test_ui.py` (a fake `colab sessions`, `colab usage` and probe; no test runs the real CLI).

## Dashboard
`/dashboard` (`static/dashboard.html`, `static/dashboard/`) has three tabs, each with its own address on the same page: **Debian** (`/dashboard`, `<debian-tab>`, the container stats below), **Agents** (`/dashboard/agents`, see the Agents section) and **Colab** (`/dashboard/colab`, see the Colab section). `dashboard-page.js` draws the tab bar and mounts only the shown tab (a hidden tab does no polling); switching uses `history.pushState`, so there is no reload and back/forward move between tabs (`static/dashboard/tabs.js`, DOM-free, tested in `tests/js/agents.test.mjs`). The header's `.dash-status` truncates long messages with ellipsis and exposes the full text on hover (`title`). The Debian tab is Pandora's stat-card grid and Top Processes table for the container Hive runs in. `ContainerMonitor` (`src/infrastructure/system/monitor.py`, psutil) reads the cgroup (v2, then v1) so CPU is the share of the container's CPU limit (`cpu.max`, delta of `cpu.stat usage_usec` between calls spaced at least 0.5 s apart; the first call reports 0) and memory is `memory.current` minus `inactive_file` against `memory.max` (host total when unlimited), like `docker stats`. `GET /api/system/stats` gives cpu, memory, load average, process/thread counts, `storage` (the home folder in three pieces that do not overlap: Notes = `NOTES_DIR` incl. `.git`, Downloads = `~/Downloads`, Home = the rest of `~`; walked in a background thread and cached 5 min, `{pending: true}` until the first walk ends), uptime (PID 1) and Hive's own rss/threads/open files (the page shows one row of four cards: CPU, Memory, Load Average with threshold-coloured values, and Storage: Home / Notes / Downloads); `GET /api/system/processes?page&page_size&sort=cpu_percent|mem_percent&direction` is a server-sorted page of the container's processes (handles are kept between calls so `cpu_percent` is a delta, newly seen PIDs are primed once without an immediate second read, and one sweep with cached names/command lines is shared for 2 s). The storage card's caption is what is free on the disk the home folder is on (`40.2 GB free of 453 GB disk`; `disk` in the stats, from `statvfs`; the free figure is green until three quarters full, yellow to nine tenths, then red; the bar is the home folder as a share of the disk, split Home / Notes / Downloads, with the bare track after it being the rest of the disk; a piece under 1.5% keeps a sliver; the split is also in the tooltip), carries a breakdown tooltip (`storageTooltipDetails`) so clipped sizes stay readable, and sizes are what a file costs on disk (never more than its blocks, a hardlink once). The Debian and Colab tables share their columns (`static/dashboard/process-columns.js`; Debian adds Threads and Status). A Debian row carries a `project` (as in Pandora): the repository holding the virtual environment in its command (`.venv/bin/python`), else the one holding its working folder (a coding agent's own folder when there is no repository), shown in blue after the name; `~` and `/` name nothing. The tab bar's tabs are real links (`href`), so a modified click opens a new tab and a plain one switches in place. The page polls both every 5 s while the tab is visible and the page is not hidden and updates the cards in place; the header shows no "Updated" time, only an error if a read fails (transient process refresh failures keep the last rows on screen). Card and column logic without DOM is in `static/dashboard/format.js` (tests: `tests/js/dashboard.test.mjs`, `tests/infrastructure/test_system_monitor.py`, `tests/api/test_system_api.py`).

## Commit messages from Codex
`HIVE_COMMIT_MESSAGES=codex` (off by default; **the note's diff is sent to the model**) improves the message of each add/edit commit. The save still commits at once as `doc: update Title`; a background thread (`src/infrastructure/git/rewording.py`) then runs `codex exec` once (`src/infrastructure/agents/codex.py`, the same flags as Pandora's workflow agent step: read-only sandbox, no user config; `--ephemeral`, so a reword saves no session and never shows in ccusage (otherwise every save was its own row), prompt on stdin, answer from `-o`) and replaces the message with its subject (`GitClient.reword`). Only the message changes: `reword` keeps tree, author and dates, builds the commit with `commit-tree` and moves `HEAD` with a compare-and-swap, never touching the index or working tree. It skips a commit that is no longer the tip (a newer save landed first), has other than one parent, or is already on a remote branch, and any failure keeps the plain message. Rename, delete, restore and `update_many` (time moves) keep their own messages. Because the sha changes, a History list opened before the reword may hold a stale sha. `/api/metrics` counts `commit_message_reworded`, `commit_message_kept`, `commit_message_errors` and times `commit_message`. `HIVE_CODEX` sets the program, `HIVE_CODEX_MODEL` the model, `HIVE_CODEX_EFFORT` the reasoning effort (passed as `-c model_reasoning_effort=...`); `HIVE_CODEX_COMMIT_MODEL` / `HIVE_CODEX_COMMIT_EFFORT` override them for commit messages only, and the chat has `HIVE_CODEX_CHAT_MODEL` / `HIVE_CODEX_CHAT_EFFORT` (`codex_setting`, `src/api/main.py`).

## Note history
`GET /api/notes/{slug}/versions?limit&offset&kind` (newest first; no `limit` = all; `kind` keeps the versions that include that kind of change and `limit`/`offset` then count matches, so the drawer's filter tabs ask the server and reach past the first page) returns each commit with `added`/`removed` line counts and, from `src/domain/notes/changes.py` (`describe`, which compares the note with the commit before it), `kind` (icon: text, properties, time, restore, rename, created, saved), `kinds` (every kind present, for the filters), `summary` ("Moved to Done", "Logged 1h 30m", "Edited text") and `detail` (the section edited, the day logged). Parsed versions are cached per commit in the repository. The drawer (`static/notes/history.js`, DOM-free pieces in `history-list.js`) pages 30 at a time, groups by day, filters by kind (server side), and shows one version as its changed frontmatter keys (`properties`: old and new value, `updated` dimmed) plus a numbered text diff with changed words marked, against the previous version or the current note (`GET .../versions/{sha}/diff?against=previous|current`, which also returns `index`/`total`, `version_title` and `current_title`). Restore asks for confirmation and says if the file will be renamed.
History speed: `git log --follow` walks the whole repository (about 0.4 s on a 1300-commit vault), so `FileNoteRepository._history` reads a note's full history once and keeps it until `HEAD` moves; list pages, diffs and restores are cut from it, and `compare()` (the diff route) uses it plus parsed versions cached per commit. A commit that deleted the note is listed (`deleted`, kind `deleted`, a disabled row) but has no content to open or restore. The drawer shows a placeholder at once, caches fetched diffs, prefetches a row's diff on hover and both neighbours of the open version, and drops a response that arrives after another version was opened.

## Codex sessions (chat and commit messages)
Neither is ephemeral and neither forgets: `SessionStore` (`src/infrastructure/agents/sessions.py`, `HIVE_STATE_DIR/codex-sessions.json`) keeps one Codex session id for the chat (`chat`) and one for the commit messages (`commit`) on the server, so every browser and every restart carries on in the same session (`codex exec resume <id>`; if a session cannot be resumed a new one starts and replaces it). "New chat" calls `DELETE /api/chat/session`. The commit-message session starts anew each calendar month (the month is saved with its id as `commit.tag`; an id without it counts as old), so it never grows for ever; the chat session lasts until "New chat". It runs in `NOTES_DIR` with no shell (it only answers); its worker is one thread, so runs never overlap. Tests point `HIVE_STATE_DIR` at a temp folder (`tests/conftest.py`).

## Chat
`/chat` (`static/chat.html`, `<chat-app>` in `static/chat/`) asks questions of the notes and can change them. The answers come from **Codex** (`codex exec --json`), never an API: Pandora's chat look (avatars, borderless messages, composer bar), none of its model picker, conversation list or database. **A chat is one Codex session, remembered by the server** (`SessionStore`, see Codex sessions). Codex is not `--ephemeral`, so it keeps the session in its own logs (that is how ccusage counts chat tokens on the Agents tab, one row per chat). The first question starts it and the `thread.started` line becomes a `session` event; the page keeps the id (`localStorage` key `hive:chat-session`) and sends it back (`POST /api/chat` `{messages: [{role, content}], session?}`, last message a `user` one; `session` must be a UUID). With a session the server runs `codex exec resume <id>` with only today's date and the question (rules and the vault's AGENTS.md went in with the first question and are not re-sent); if the resume fails before any event (session file gone) it starts a new session with the last 12 turns replayed, and the new `session` event replaces the id. Codex always works in the same empty folder (`~/.local/state/hive/chat`, `HIVE_STATE_DIR`): a resumed session remembers its folder. `exec resume` has no `--sandbox`/`-C`, so it gets `-c sandbox_mode="read-only"`. The conversation is kept in the browser (`localStorage` key `hive:chat`, last 40 turns, `restoreTurns`/`serializeTurns` in `static/chat/format.js`), so it is still there after leaving the page or reloading; "New chat" clears turns and session. A turn that was running when the page closed comes back stopped (leaving closes the stream, which stops Codex), its unfinished steps failed.
- **Codex works in the notes with its own shell, unsandboxed.** `CodexChat` (`src/infrastructure/agents/codex_chat.py`) runs `codex exec --json --dangerously-bypass-approvals-and-sandbox -C NOTES_DIR` (resume: the same flag, the process's cwd is `NOTES_DIR`), because bubblewrap cannot start where there are no user namespaces. It reads with rg/cat, edits with sed and commits itself (`git add -- <files> && git commit`, only its own files; the rules in `SYSTEM`, `src/application/chat/service.py`), and follows the vault's AGENTS.md, which it is told to read. There are no Hive tools and no MCP server. **There is no sandbox and Hive has no login: anyone who can reach the port can make Codex run commands.** Keep the port on this machine (publish `-p 127.0.0.1:80:80`; `LocalhostOnly` checks the Host header, which a non-browser client can fake). Its edits do not go through `NoteService`, so renames and link rewriting are up to Codex; the watcher and the end-of-run `invalidate` pick the changes up.
- **Prompt** (`build_prompt`, `src/application/chat/service.py`): `SYSTEM` (shell rules: answer from the notes, cite `[[Title]]`, change notes only when asked, smallest edit, commit only your own files, never discard or push), today's date, then the turns. A resumed session gets only today's date and the question. Codex is told to read the vault's `AGENTS.md` itself.
- **Events** (SSE `data:` lines; `src/domain/chat.py` `parse_line` maps Codex's JSON lines): `step` (a shell command or file change: `label` is the command, `write` is guessed from it, `status` running/done/failed), `message` (Codex text: the newest is the answer, earlier ones show as narration), `done`, `error`, then `changed` (`{slug, title}` of the notes the commits between HEAD before and after touched, so renames are right). A client that leaves (Stop button, closing the tab) closes the stream, which kills Codex; a run is killed after 600 s. Edits already saved stay saved (History on the note undoes them).
- **Work folds away** (`static/chat/steps.js`, DOM-free, tests in `tests/js/chat.test.mjs`): while Codex runs the answer shows the newest `LIVE_STEPS` (4) steps and "+N earlier"; when the turn ends they fold into one closed `<details class="chat-work">` line above the answer: "Worked for 14s · 9 steps · changed 1 note" (a pen when something was saved). It opens by itself when a step failed or the turn errored. Each step shows `friendlyLabel` (“Searched notes for “wifi””, “Read home.md”, “Committed: doc: …”; anything unrecognised keeps its command) with the raw command beside it. The turn keeps `startedAt`/`endedAt` (saved with the conversation) for the duration. The server's step label is the command cut to 240 characters.
- **Config:** `HIVE_CODEX` (program), `HIVE_CODEX_MODEL`, `HIVE_CODEX_EFFORT`, as for commit messages, each overridden for the chat by `HIVE_CODEX_CHAT_MODEL` / `HIVE_CODEX_CHAT_EFFORT`. Without Codex `GET /api/chat/status` says so and the page disables sending. The note's text is sent to the model, as with `HIVE_COMMIT_MESSAGES=codex`. Like everything else here there is no login: anyone who can reach the port can read and change notes through the chat.
- **Beside a note** (`<chat-app compact note="<slug>">`, docked in the note page; the same component and server as `/chat`, tests in `tests/api/test_chat_api.py` and `tests/browser/test_ui.py`): the chat button in the note's footer (Ctrl/⌘+Shift+L; the open/closed choice is kept in `localStorage` `hive:note-chat-open`) opens a panel *beside* the note, not an overlay, so the note redraws live while the agent edits it. Read or edit mode is left as it is; unsaved new notes have no panel. Table and timeline pages have it too (below). `POST /api/chat` takes `note` (a slug; unknown is an `error` event, a name that is not a plain slug is 422) and `selection` (text selected in the note, cut to 4000 characters): `note_scope` (`service.py`) tells the agent which file "this note" is, to change only it unless asked and quotes the selection, in the first prompt and in every resumed one. **Each note has its own conversation:** its own session on the server (`chat:note:<slug>`, also `chat-agy:` / `chat-claude:`; `DELETE /api/chat/session?note=<slug>` forgets only that one, the page's "New chat" leaves them alone) and its own turns in the browser (`hive:chat:note:<slug>`, `noteKeys` in `static/chat/format.js`). **Renames:** an edit to the heading renames the file, so after a run whose note is gone `ChatService` finds the rename with `git diff -M20%` (the low threshold is for small notes), moves the session and adds `renamed: {from, slug, title}` to the `changed` event; the chat rekeys its stored turns and, when the run ends (`chat-finished`), the page goes to the new address. While a run is going on, the page's "note renamed or deleted elsewhere" reaction is held back (leaving would stop the agent). **The page** (`ensureChat`, `mountChat` in `notes-page.js`) keeps one chat element and moves it into each redraw (`disconnectedCallback` only stops a run if the element is still out of the page after the task, so a redraw does not cut it; closing the panel only hides it). Before a question is sent `beforeSend` saves unsaved editor text (one commit), so the agent reads the note as it is; text selected in the preview or the editor (mouseup/keyup in the note) is shown as a chip above the box and sent with the next question only. A note changed by a run shows a "View changes" button that opens the History drawer; links in answers go through the page's `go` (unsaved-edit prompt, no reload).
- **On table and timeline pages** (`defineReadPage`, `static/notes/read-page.js`): the dock (shared `NoteChatDock`, `static/notes/note-chat.js`, also used by the note page) is a column fixed to the window's right edge, because those pages scroll with the window; the page makes room (`padding-right`) and the footer bar stops at the dock. A view's footer carries the button (`chatButtonHtml`, `actions.chat` / `actions.chatOpen`); open or closed is shared with the note page. These pages also **follow their note**: `watchChanges({note})` fetches the note and compares `revision` (own saves are recognised: a view's `busy()` says 'saving' while its save is out, and the page waits); a changed note is drawn again with the view's filter, sort and page kept. While a row is open in the table's drawer (`busy()` = 'editing', a modal) a toast says so and the change is drawn once it is closed; a note renamed or deleted while the chat is running is held until the run ends (`chat-finished` then follows a rename). Text selected in the page goes with the next question as on the note page.
