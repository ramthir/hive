# Hive

File-backed notes app: markdown files in `NOTES_DIR` (default `~/Workspace/notes`), versioned with git (one commit per save/rename/delete). Based on ~/Workspace/pandora's notes feature, without the database.

- Tests: `uv run pytest` (single file: `uv run pytest tests/<path>`). It also runs the Node unit tests in `tests/js/` (`tests/test_js_units.py`; skipped without `node`). Browser tests in `tests/browser/` need `uv run playwright install chromium` and are skipped when Chromium cannot launch, so a green run may not have exercised the UI.
- Every new feature needs automated tests next to the existing ones in `tests/`.
- Layers: `src/domain` (entities, ports) -> `src/application` -> `src/infrastructure` (git, fs_notes) -> `src/api`.
- A note's title is its first `# heading`; its file name is the kebab-case of that title (never set by hand). Changing the heading renames the file (service rewrites `[[slug]]`/`[[Title]]` links). Notes whose file has no heading show the frontmatter title as one until saved. `/` and `/notes` open the most recently edited note: there is no list page.
- Note identity is the filename slug. Frontmatter (`title`, `tags`, `created`, `updated`) is round-tripped with ruamel so diffs stay minimal.
- Never run tests against the real notes dir; use temp git repos.

## API
Under `/api`: `GET/POST /notes`, `GET/PUT/DELETE /notes/{slug}`, `/notes/{slug}/backlinks`, `GET /notes/{slug}/properties`, `/notes/{slug}/versions[/{sha}[/diff]]`, `POST /notes/{slug}/versions/{sha}/restore`, `GET /latest`, `GET /resolve` (wiki links), `GET /tasks`, `GET /tasks/current-week`, `GET /time-entries`, `GET /time-notes`, `PUT/DELETE /notes/{slug}/time/{day}`, `POST /notes/{slug}/time`, `GET /tags`, `GET /types`, `POST /reindex`, `POST /diagram/render`, `GET /diagram/status`, `GET /metrics`, `GET /system/stats`, `GET /system/processes`, `GET /agents/usage`, `GET /agents/usage/sessions`, `GET /health`. Pages: `/`, `/notes[/...]`, `/tables/{slug}`, `/tasks`, `/time-entries`, `/dashboard[/agents]`. `/tags` and `/types` feed the note page's tag and type comboboxes.
`GET /api/notes/{slug}` returns a `revision` (hash of the file's text). `PUT /api/notes/{slug}` accepts it back: if the file changed since (another tab, an editor, `git pull`), nothing is written and the answer is 412; the note page then asks before overwriting. Requests without `revision` (task board, drawers) are never refused.

## Performance monitoring
- Live: `GET /api/metrics` -> counters (`watcher_batches`, `watcher_events`, `index_invalidations`), timings (`index_rebuild`, `git_commit`: count/avg/max ms) and process stats (`cpu_s`, `rss_kb`, `threads`). Poll `cpu_s` twice to get CPU use over an interval.
- Benchmark: `uv run python scripts/bench.py <COPY of notes> [--with-hook] [--no-watch]` (edits files and commits: use a copy).
- Design: the watcher (watchfiles/inotify, `step=250ms`, `debounce=400ms`) only invalidates the index; it is rebuilt lazily on the next request, so bursts coalesce into one rebuild and an idle app does nothing. The rebuild is incremental twice over: `FileNoteRepository.list()` re-parses only files whose (mtime, size) changed, and the watcher and service writes name the slugs they touched, so `NoteIndex.updated` patches just those notes (`index_patch` timing; copy-on-write, so readers never see a half-updated index). More than `PATCH_LIMIT` (50) changed notes, `POST /api/reindex` or a file the repository cannot load by name fall back to a full rebuild.
- `commit --only` runs hooks on a temp index, so `GitClient.commit_paths` re-syncs the real index afterwards; do not remove that or formatter hooks leave phantom staged changes.

## Layout
Hive is a desktop app: there is no mobile or narrow-screen layout (no `@media` width queries, no sidebar menu button). Pages are laid out for a wide window and the sidebar is always a left column that can be collapsed (Ctrl/⌘+\\ or B). Do not add breakpoints.

## Running
`NOTES_DIR=~/Workspace/notes uv run python main.py` serves on port 80 (needs `net.ipv4.ip_unprivileged_port_start` <= 80 or root). Binds 0.0.0.0 by default and there is no auth, so anyone who can reach the port can edit notes; `HOST=127.0.0.1` limits it to this machine. `PORT` overrides the port. `HIVE_WATCH=0` turns the file watcher off (edits made outside Hive are then only seen after `POST /api/reindex`). `GRAPHVIZ_DOT` points at Graphviz `dot` when it is not on PATH. Every save is a real git commit in `NOTES_DIR`.

`scripts/service.sh start|stop|restart|status|ensure` runs it in the background without systemd (pid and log in `~/.local/state/hive/`; it also finds a `main.py` started by hand from this directory). It does not survive a reboot or a container restart: start it again.

## PlantUML previews
Fenced ```plantuml / ```puml blocks render as images in the preview. `DiagramService` (`src/application/diagrams`) runs `java -jar plantuml.jar -pipe -tsvg` per diagram (~200 ms) under `PLANTUML_SECURITY_PROFILE=SANDBOX`, so the renderer itself reads no files and opens no URLs; `!include <file>.puml` is inlined by us, only from `NOTES_DIR` and never outside it, and `!include monokai-theme.puml` / `!theme monokai-pro` always use the bundled theme (as in Pandora). Results are cached by source hash. The SVG is shown through an `<img>` data URL, never inline, so a diagram cannot run script.
Setup (no root needed): a JRE (`mise install java@temurin-21`) and `plantuml.jar` in `~/.local/share/hive/plantuml/` (verify the SHA-256 GitHub publishes for the release), then `PLANTUML_JAVA` / `PLANTUML_JAR` in `.env`. Without them the code block stays and a message says why.
Fonts (`apt-get install fontconfig fonts-dejavu-core`, needs root) are required too: on a machine without fontconfig Java dies with `Fontconfig head is null` and every diagram fails with "PlantUML produced no image". Graphviz (`apt-get install graphviz`, needs root) is needed for the theme's boxed connectors: PlantUML still draws class/component diagrams without it, but with a layout that ignores `LineType ortho`, so lines come out diagonal. `/api/diagram/status` reports `graphviz`, and a real-Java test fails if it is missing. Mindmaps do not use Graphviz; their connectors are always curved.

## Frontmatter conventions (match the vault)
`tags` is an inline list (`tags: [a, b]`); `type` is a single value (`type: task`), or an inline list when a note has several. Hive reads block lists, inline lists and scalars, and only rewrites `tags`/`type` when they actually change; a changed value is written in the convention above. Types map to icons and icon colours (`TYPE_COLORS`, palette tokens; shown in the note search) in `static/type-icons.js` (add a vault type there; `tests/js/type-icons.test.mjs` fails if a name is not in the vendored Font Awesome).

## Task board
`/tasks` (`static/tasks.html`, its own document, so sidebar links to Notes are full navigations) shows every note of `type: task` as a card on a To Do / In Progress / Done board (`GET /api/tasks`; board component from Pandora). Dragging a card sends `PUT /api/notes/{slug}` with `status`: one normal git commit.
- **Status:** frontmatter key `status` (`TODO`, `IN_PROGRESS`, `DONE`), written after `type` and only when it changes. Notes without one (older vault notes) get a derived status: `done` in `tags` means Done, else To Do. A stored status wins over the tag.
- **Week:** `week: 2026-W47` (ISO week a task was finished), written after `status`. Set when a task moves to Done (the service's clock), cleared when it leaves Done, or set by hand through the API. The server does all the week maths: each task carries `week_key` (its `week`, else the week of `updated`) and `week_stored` (which of the two); `GET /api/tasks/current-week` gives the Done pill's default. The page never computes weeks and reloads `/api/tasks` after a save.
- **Done pill:** Pandora's week dropdown in the Done header (weeks with finished tasks, newest first with counts, this week always listed, then All weeks). Starts on this week; the choice lives in the address (`/tasks?done=2026-W47` or `?done=all`). Open tasks are never filtered.
- **Priority:** frontmatter key `priority` (`must`, `important` or `nice-to-have`), written after `status` and only when it changes. Older vault notes mark it with a tag of the same name (leading `#` ignored; the most urgent wins); a stored `priority` wins over the tag, and `/api/tasks` leaves priority tags out of `tags`. `PUT /api/notes/{slug}` takes `priority` (`""` removes it): it sets the key and drops any priority tag from the given (or current) `tags`, so a note migrates the first time its priority is saved (`src/domain/notes/tasks.py`). Cards show a ranked chip; each column sorts Must, Important, Nice to have, none (stable) in the page, not on the server.
- **Card and drawer:** Cards show the task's `ticket` (set in the properties drawer, returned as `ticket` by `/api/tasks`) as the first chip. logic in `static/tasks/card.js` (tests: `tests/js/task-card.test.mjs`). Clicking a card opens the note properties drawer (`openProperties`, the same code as the note page); it sends only the changed keys in one `PUT` (one commit, plus the rename commit when the title changes). The card's arrow goes to the note. Week is editable there too.

## Time entries
Time is logged on notes of `type: task` or `meeting` (a note that is both counts as a task) in the `time` frontmatter key: a map of ISO day to minutes, one total per day, written inline after `week` (`time: {2026-11-20: 90, 2026-11-21: 45}`). Days are 1-1440 minutes. Domain in `src/domain/notes/time.py`; the repository only rewrites the key when the usable days change and keeps entries that are not a valid day and minutes (a hand-typed `soon: 30` survives). Logging time is a normal save, so it is one git commit and bumps `updated` like any save.
- **Write:** `NoteService.log_time(slug, day, minutes, add=False)` / `remove_time`. `PUT /api/notes/{slug}/time/{day}` sets the minutes (1-1440), `POST /api/notes/{slug}/time` (`{day, minutes}`) adds to the day, `DELETE .../time/{day}` removes it (404 if the day is absent). `POST .../time/{day}/move` (`{slug, day, minutes}`) moves a day to another note and/or day, adding to what is there, in one commit (`NoteService.move_time`, `FileNoteRepository.update_many`). Time left on a note that is no longer a task or meeting still shows as a row of type `other` (warning icon) so it can be deleted; it is not offered in the picker. A note that is not a task or meeting, a bad day or a day over 1440 minutes is a 422. `GET /api/notes/{slug}` returns the map as `time`.
- **Read:** `GET /api/time-entries?q&start&end&note&page&page_size` returns one row per note and day (`id` is `slug:day`; newest day first, then title) plus the current month (the server's clock: `month`, `today`) over every match: `total_entries`, `total_minutes`, `task_minutes`, `meeting_minutes`, `today_minutes` and `days` (each day with time: its minutes and the `{title, project, minutes}` it was spent on). `q` is free text on the title plus Pandora's `project:`, `task:`, `date:today|yesterday|YYYY-MM-DD`, `duration:>30m` (`<`, `>=`, `<=`, `45`, `30m-2h`) filters; an unreadable `date:` or `duration:` matches nothing; a filter swallows the text after it, so put free text first (quote a multi-word value: `project:"Big Co"`). `project` is an optional `project:` frontmatter key. The search and summary live in `src/application/notes/time_entries.py`.
- **Page:** `/time-entries` (`static/time-entries.html`, `static/time-entries/`): Pandora's three stat cards (`static/components/stat-card.js`, `activity-sparkline.js`: Total Logged with the month's sparkline and the 160h month / 8h day progress, Task Work, Meetings; built by `summaryTiles` (`summary.js`) from the server's month, so the page does no date maths), the table, paging and an add/edit drawer, using Pandora's table, pagination, date/duration pickers and CRUD drawer (copied into `static/components/`). The search and page are kept in the address (`?q=&page=`). The drawer's note picker comes from `GET /api/time-notes`: tasks and meetings only, this week's first (edited this week or with time logged this week, by the service's clock; newest first), then the rest by title, with "This week" / "Earlier" headings (a `group` on a combobox option draws a heading where it changes). Logic without DOM is in `static/time-entries/` (`format.js` durations and days, `summary.js` the stat cards, `logged.js` the note page's helpers, `entries.js` table, address and `savePlan`; tests: `tests/js/time-entries.test.mjs`); `savePlan` turns the drawer into API calls (adding adds to the day; moving a row to another note or day adds there and removes the old row). On the note page a task or meeting note has a clock button ("Log time", `static/notes/log-time.js`: date and duration, adds to the day) and a "3h 30m logged" chip in the footer; logging commits only the `time` key and leaves unsaved editor text alone.

## Note properties drawer
The sliders button in a note's footer (Ctrl/⌘+Shift+P) opens Pandora's properties drawer, titled for the type ("Task Properties", "Contact Properties"...; `title` of `GET /notes/{slug}/properties`), with fields that depend on the note's `type`. Pandora keeps these as links between notes; here each field is a frontmatter key (`project: Acme`), so there is no database and a note that links by title does not follow a rename.
- **Forms:** `src/domain/notes/properties.py` (`FORMS`, keyed by lower-case type; the first of a note's types with a form wins, so task beats meeting). Task: project, specification, ticket (Ticket ID, free text), status, priority, assignee, week, tags. Meeting: week, project. Project: billing (Billable / Non Billable / Prospecting). Contact: role, project, team, billing (adds Shadowed), acting_for (shown and required only while billing is Shadowed). Spec: project, application. Prompt: project. A type with no form has no button (`has_properties` on `GET /api/notes/{slug}`). Add a type there and the drawer follows; the page has no per-type code.
- **Field targets:** `tags`, `status`, `priority` and `week` are the keys the task board already manages (changed tags are sent with the priority, since the server drops a priority tag from the tags it is given), so the drawer and the board agree; every other field is its own key and lands in `extra`. A `note` field is the title of a note of the given types (the choices come from the index; a hand-typed value stays selectable); a `select` field is a fixed list.
- **API:** `GET /api/notes/{slug}/properties` returns the groups and fields with `value` and `choices` (404 if the type has no form). `PUT /api/notes/{slug}` takes `properties` (`{"project": "Acme"}`, `""` removes a key; unknown keys, bad select values and a missing required field are 422) next to `status`/`priority`/`week` (`week: ""` clears it). `src/application/notes/properties.py` builds the form view.
- **UI:** `static/notes/properties.js` (drawer) and `property-fields.js` (DOM-free: visibility, `propertyChanges`, field markup; tests: `tests/js/property-fields.test.mjs`). Saving sends only the changed fields in one PUT, so it is one commit. Unsaved editor text is saved first.

## Agents
The Agents tab of the dashboard (`/dashboard/agents`, `<agents-tab>` in `static/agents/`) shows this month's token usage of the coding agents Claude, Codex and Antigravity: a card per provider (Totals, Input, Cached, Output, sessions, models), a stacked daily chart for the month and a server-sorted, paged sessions table whose session cell copies the resume command (`claude --resume <id>`, `codex resume <id>`). Ported from Pandora's Na'vi tab without quota donuts or task links. `GET /api/agents/usage` is the view, `GET /api/agents/usage/sessions?sort&dir&page&page_size` one page of sessions (`sort`: last_activity, provider, input, cached, output, total).
- **Source:** `ccusage` (npm `ccusage`, found on PATH, then in an nvm or mise node; `HIVE_CCUSAGE` sets it) run as `ccusage --sections daily,session --by-agent --json --no-cost --offline --since <1st of month> -z <host timezone>` (`CcusageCollector`, `src/infrastructure/agents/usage_files.py`). It reads the agents' own session logs, so nothing is configured. Without it the page says so.
- **Cache and refresh (no cron):** the report is `~/.local/state/hive/agents/usage.json` (`HIVE_STATE_DIR`, the folder `service.sh` uses), replaced atomically and parsed again only when its size or mtime changes (`ReportStore`). `AgentUsage` (`src/application/agents/usage.py`) serves it and, when it is older than 15 minutes, makes a new one in a background thread, so a request never waits for ccusage: only a missing report or a new month waits (requests then share one run). A failed run keeps the old report, shows its reason once the report is over 45 minutes old, and is not retried for a minute. An idle app does nothing; the page polls once a minute while its tab is visible. `/api/metrics` counts `agents_refreshes` and `agents_refresh_errors` and times `agents_collect`.
- **Manual run:** `uv run python scripts/agents_collect.py [--output FILE] [--ccusage PATH]` makes the report now and prints the totals (exit 1 with the reason if ccusage fails).
- **Domain:** `src/domain/agents/usage.py` (`parse_envelope`, `build_view`, `session_page`). ccusage's `input` excludes cache; the view's `input` includes cache reads and writes, and `total` is input plus output. A report whose month is not the current one is never shown as this month's.
- **Tests:** `tests/domain/test_agent_usage.py`, `tests/infrastructure/test_agent_usage_files.py`, `tests/application/test_agent_usage.py`, `tests/api/test_agents_api.py`, `tests/test_agents_collect_script.py`, `tests/js/agents.test.mjs`, browser tests in `tests/browser/test_ui.py` (they inject a fake collector; no test runs the real ccusage or reads `~/.local/state`).

## Dashboard
`/dashboard` (`static/dashboard.html`, `static/dashboard/`) has two tabs, each with its own address on the same page: **Debian** (`/dashboard`, `<debian-tab>`, the container stats below) and **Agents** (`/dashboard/agents`, see the Agents section). `dashboard-page.js` draws the tab bar and mounts only the shown tab (a hidden tab does no polling); switching uses `history.pushState`, so there is no reload and back/forward move between tabs (`static/dashboard/tabs.js`, DOM-free, tested in `tests/js/agents.test.mjs`). The Debian tab is Pandora's stat-card grid and Top Processes table for the container Hive runs in. `ContainerMonitor` (`src/infrastructure/system/monitor.py`, psutil) reads the cgroup (v2, then v1) so CPU is the share of the container's CPU limit (`cpu.max`, delta of `cpu.stat usage_usec` between calls; the first call reports 0) and memory is `memory.current` minus `inactive_file` against `memory.max` (host total when unlimited), like `docker stats`. `GET /api/system/stats` gives cpu, memory, load average, process/thread counts, `storage` (the home folder in three pieces that do not overlap: Notes = `NOTES_DIR` incl. `.git`, Downloads = `~/Downloads`, Home = the rest of `~`; walked in a background thread and cached 5 min, `{pending: true}` until the first walk ends), uptime (PID 1) and Hive's own rss/threads/open files (the page shows one row of four cards: CPU, Memory, Load Average, Storage: Home / Notes / Downloads); `GET /api/system/processes?page&page_size&sort=cpu_percent|mem_percent&direction` is a server-sorted page of the container's processes (handles are kept between calls so `cpu_percent` is a delta; one sweep is shared for 2 s). The page polls both every 5 s while the tab is visible and updates the cards in place; the header shows no "Updated" time, only an error if a read fails. Card and column logic without DOM is in `static/dashboard/format.js` (tests: `tests/js/dashboard.test.mjs`, `tests/infrastructure/test_system_monitor.py`, `tests/api/test_system_api.py`).

## Table notes
A note whose `type` includes `table` is read on its own page, `/tables/{slug}` (`static/tables.html`, its own document like `/tasks`; all its code is in `static/tables/`). Opening `/notes/{slug}` of a table note in read mode redirects there; the pencil goes to `/notes/{slug}?mode=edit` and closing the editor comes back. `/tables/{slug}` sends a note that is not a table to `/notes/{slug}`.
`table-note.js` (DOM-free; tests: `tests/js/tables.test.mjs`) parses the first markdown table of the text and writes it back, keeping all text around it; `table-view.js` is the view (filter, sort, 15-row paging, optional stat cards from a ````json table-config``` block, add/edit/delete row drawer); `tables-page.js` loads the note and handles the footer buttons. Every row change is a normal `PUT /api/notes/{slug}` with the whole new `content`: one git commit. Cells with `[[Title]]` link to the note (resolved through `/api/resolve`); a column of linked cells, or one headed Employee/User/Owner/Assignee/Contact/Person, gets a multi-select in the drawer, offering notes of `type: contact`.

## Commit messages from Codex
`HIVE_COMMIT_MESSAGES=codex` (off by default; **the note's diff is sent to the model**) improves the message of each add/edit commit. The save still commits at once as `doc: update Title`; a background thread (`src/infrastructure/git/rewording.py`) then runs `codex exec` once (`src/infrastructure/agents/codex.py`, the same flags as Pandora's workflow agent step: read-only sandbox, ephemeral, no user config, prompt on stdin, answer from `-o`) and replaces the message with its subject (`GitClient.reword`). Only the message changes: `reword` keeps tree, author and dates, builds the commit with `commit-tree` and moves `HEAD` with a compare-and-swap, never touching the index or working tree. It skips a commit that is no longer the tip (a newer save landed first), has other than one parent, or is already on a remote branch, and any failure keeps the plain message. Rename, delete, restore and `update_many` (time moves) keep their own messages. Because the sha changes, a History list opened before the reword may hold a stale sha. `/api/metrics` counts `commit_message_reworded`, `commit_message_kept`, `commit_message_errors` and times `commit_message`. `HIVE_CODEX` sets the program, `HIVE_CODEX_MODEL` the model, `HIVE_CODEX_EFFORT` the reasoning effort (passed as `-c model_reasoning_effort=...`).

## Note history
`GET /api/notes/{slug}/versions?limit&offset&kind` (newest first; no `limit` = all; `kind` keeps the versions that include that kind of change and `limit`/`offset` then count matches, so the drawer's filter tabs ask the server and reach past the first page) returns each commit with `added`/`removed` line counts and, from `src/domain/notes/changes.py` (`describe`, which compares the note with the commit before it), `kind` (icon: text, properties, time, restore, rename, created, saved), `kinds` (every kind present, for the filters), `summary` ("Moved to Done", "Logged 1h 30m", "Edited text") and `detail` (the section edited, the day logged). Parsed versions are cached per commit in the repository. The drawer (`static/notes/history.js`, DOM-free pieces in `history-list.js`) pages 30 at a time, groups by day, filters by kind (server side), and shows one version as its changed frontmatter keys (`properties`: old and new value, `updated` dimmed) plus a numbered text diff with changed words marked, against the previous version or the current note (`GET .../versions/{sha}/diff?against=previous|current`, which also returns `index`/`total`, `version_title` and `current_title`). Restore asks for confirmation and says if the file will be renamed.
History speed: `git log --follow` walks the whole repository (about 0.4 s on a 1300-commit vault), so `FileNoteRepository._history` reads a note's full history once and keeps it until `HEAD` moves; list pages, diffs and restores are cut from it, and `compare()` (the diff route) uses it plus parsed versions cached per commit. A commit that deleted the note is listed (`deleted`, kind `deleted`, a disabled row) but has no content to open or restore. The drawer shows a placeholder at once, caches fetched diffs, prefetches a row's diff on hover and both neighbours of the open version, and drops a response that arrives after another version was opened.
